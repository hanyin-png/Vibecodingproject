> 《制造智能技术》课程设计

## 1. 背景调研

### 1.1 研究背景与意义

制造业设备的维修方式大致经历了三个阶段：坏了才修的事后维修、按周期检修的定期维修、以及根据设备实际状态安排维修的预测性维护（PdM）。事后维修的停机损失大，定期维修则容易"修过头"（还能用的部件被提前换掉）或"修不够"（没撑到检修期就坏了）。

预测性维护的思路是：通过传感器持续采集设备运行数据，用人工智能方法评估设备健康状态、预测剩余使用寿命（RUL），在故障发生前安排维修。这样既能避免突发停机，又不浪费备件和工时。本次课程设计就围绕这一场景，开发了一套完整的设备健康管理系统。

### 1.2 本项目要解决的问题

对制造企业的设备运维人员来说，日常工作核心是三个问题：**设备现在状态怎么样？还能用多久？出了问题修哪里？** 本系统把这三个问题串成一条完整的业务闭环：设备台账 → 数据监测 → 健康评估 → 异常预警 → 智能诊断 → 维修工单。

## 2. 方案设计

### 2.1 总体架构

系统采用 B/S 前后端分离架构，全部功能在一台个人电脑上本地运行：

- **前端**：Vue 3 + Element Plus + ECharts，6 个功能页面
- **后端**：FastAPI，RESTful API，承载业务逻辑
- **数据库**：SQLite（5 张表），免部署、随项目拷贝
- **算法模块**：scikit-learn（随机森林、孤立森林）+ PyTorch（LSTM），模型离线训练、在线只加载推理

（架构图见 方案设计.md 技术路线一节）

### 2.2 技术选型理由

- 后端用 Python 的 FastAPI：和算法模块同语言，训练好的模型直接加载，不用跨语言；
- 数据库用 SQLite：数据量一万多行，完全够用，且不用装数据库服务，答辩现场拷过去就能跑；
- 模型离线训练、在线推理：保证演示时点一下立刻出结果，工业系统也普遍这样做；
- 诊断用规则引擎而不是大模型：工业诊断要求结论确定、可追溯，同样的异常必须给出同样的建议。

### 2.3 技术方向覆盖

| 课程技术方向 | 具体方法 | 在系统中的作用 |
|---|---|---|
| 机器学习 | 随机森林回归 | 剩余寿命预测的主力模型，驱动健康评估与预警分级 |
| 深度学习 | LSTM 时序网络 | 退化趋势建模，与随机森林做对比实验 |
| 专家系统 | IF-THEN 规则引擎（15 条规则库） | 把异常征兆转成故障定位与分层排查建议 |
| 数据挖掘 | Isolation Forest 孤立森林 | 监测数据异常检测，驱动预警自动生成 |

四个方向在系统里是串起来的：异常检测发现问题 → RUL 评估严重度 → 规则引擎给处置建议 → 工单闭环执行。

## 3. 数据资源构建

### 3.1 数据集

使用 NASA C-MAPSS 涡扇发动机退化仿真数据集的 FD001 子集（单一工况、单一故障模式：高压压气机退化）。包含三个文件：train（100 台完整寿命，20631 行）、test（100 台中途数据，13096 行，模拟在役设备）、RUL 真值（验证用）。每行 26 列：设备编号、循环数、3 个工况参数、21 个传感器读数。

### 3.2 数据预处理

预处理由 `algorithms/import_data.py` 完成，步骤：

1. 加列名（原始文件无表头）；
2. 剔除 7 个从头到尾数值不变的传感器列（s1/s5/s6/s10/s16/s18/s19），恒定数据没有信息量；
3. 构造 RUL 标签：设备最大循环数减当前循环数，超过 125 截断为 125（健康初期退化信号弱，不截断标签会失真）；
4. 传感器列做 min-max 归一化，归一化参数用 train 集拟合并存盘（scaler.pkl），推理时复用同一份；
5. 原始数据导入 SQLite：equipment 表 100 台设备台账，sensor_data 表 13096 行传感器数据。

预处理后的数据同时导出到 `data/processed/`（train_clean.csv / test_clean.csv）。数据可视化脚本 `algorithms/plot_sensors.py` 生成传感器退化趋势图（见 data/传感器退化趋势图.png），可以直观看到随循环数增加，温度类传感器上升、压力类下降的退化规律。

## 4. 系统实现

### 4.1 数据库设计

5 张表：equipment（设备台账）、sensor_data（传感器数据）、prediction（预测记录）、alarm（预警）、work_order（维修工单）。预警由预测或异常检测自动生成；工单从预警一键生成并带入诊断建议。

### 4.2 后端服务

FastAPI 实现 7 组接口（设备 CRUD、传感器查询、RUL 预测、预警、诊断、异常检测、工单），接口清单见 README.md。几个关键实现点：

- 数据库路径用 `__file__` 拼绝对路径，任何目录启动都能找到 app.db；
- 模型只在第一次请求时加载、之后常驻内存，保证接口响应速度；
- 预测接口里 RUL ≤ 90 自动生成预警并按阈值分级（≤30 严重 / ≤60 警告 / ≤90 提示），同时更新设备状态。

### 4.3 前端界面

Vue 3 单页应用，左侧导航 + 内容区布局，6 个页面：设备台账（增删改查）、数据监测（ECharts 四子图趋势曲线）、健康评估（评分卡片 + 历史记录）、预警中心（分级标签 + 标记处理）、智能诊断（规则卡片展示）、维修工单（状态流转按钮）。页面截图见 `docs/截图/`。

### 4.4 算法模块一：随机森林 RUL 预测（机器学习）

取设备最近 20 个循环，对 14 个有效传感器各提取均值、标准差、末值、趋势斜率 4 个统计量，加上当前循环数构成 57 维特征，训练 RandomForestRegressor（100 棵树，限制深度 12 控制模型体积）。

**test 集评估结果：MAE = 11.84，RMSE = 15.50（单位：循环数）**，即平均预测误差约 12 个循环。

### 4.5 算法模块二：LSTM 时序建模（深度学习）

用长度 30 的滑动窗口构造时序样本（样本数 × 30 × 14），网络为两层 LSTM（隐藏维度 64，层间 Dropout 0.2）加全连接层输出寿命值，CPU 训练 30 轮。

**test 集评估结果：MAE = 11.91，RMSE = 16.18**，与随机森林（MAE 11.84 / RMSE 15.50）几乎打平。分析原因：FD001 是单工况小数据集，随机森林依赖人工提取的统计特征（均值、趋势斜率等），先验信息利用得充分；LSTM 需要从原始时序中自己学规律，在数据量不大时优势发挥不出来。这也说明深度学习并非任何场景都优于传统机器学习，特征工程的质量在小数据场景下更关键。

### 4.6 算法模块三：故障诊断规则引擎（专家系统）

自建 15 条 IF-THEN 规则（字典列表实现，不引入外部框架），分三类：A 类部件级规则 9 条（按异常传感器组合定位疑似故障部位）、B 类寿命阈值规则 3 条、C 类兜底排查规则 3 条。排查步骤按"先软后硬、先外后内"分层：先排除传感器本身和数据链路问题，再怀疑设备本体。

典型效果：对退化末期的 20 号设备诊断，规则 A1"高压压气机（HPC）退化"排在命中结果第一位，与 FD001 的真实故障模式一致。

### 4.7 算法模块四：孤立森林异常检测（数据挖掘）

IsolationForest 在 train 集的健康前段（前 30% 循环）数据上无监督训练。检测时对设备最近 20 循环打分，命中异常即自动生成"传感器异常"预警，并用 3σ 规则（与设备自身健康基线对比）列出具体的异常传感器，作为规则引擎的输入。

## 5. 测试与集成调试

### 5.1 自动化测试

使用 pytest 编写了 14 项测试，覆盖：后端各接口（增删改查、预测、诊断、异常检测、工单）、规则引擎规则命中（至少 3 条）、以及一条完整的业务闭环联调测试（预测→预警→诊断→工单→状态流转→预警处理）。全部通过。

### 5.2 调试过程中的典型问题

（写进开发中实际遇到并解决的问题，例如：）

1. 多传感器共用一个坐标轴时趋势看不清，改为 2×2 子图各自自适应；
2. 健康评估页结果一闪而过——"刷新历史"函数误清了本次结果，拆分函数职责后修复；
3. 异常标注最初用全机群 3σ 基线，灵敏度不足（台间差异大于单机退化幅度），改为设备自身健康基线；
4. 随机森林不限深度导致模型文件近 90MB，超过 GitHub 限制，限制深度后缩到 13MB 且精度几乎不变。

## 6. AI 使用披露

### 6.1 使用的工具

全程使用 Kimi Code（VSCode 插件）+ Kimi K3 模型协作开发。所有会话记录备份在仓库 `prompt/` 目录（jsonl 格式，每阶段同步更新）。

### 6.2 关键 prompt 策略

- **项目规则文件**：先写好 `docs/PROJECT_RULES.md`（技术栈、目录结构、开发规则），让 AI 每次开发前先读规则再动手，保证风格统一、不引入规格外依赖；
- **小步实现**：每次只让 AI 做一个功能点，给出验证方法（curl 命令/预期输出），我验证通过后再下一步；
- **过程留痕**：每个功能点完成后立即 git 提交，关键交互及时备份。

### 6.3 AI 出错案例与纠正

（从 prompt 记录里挑 2~3 个写，例如：）

1. AI 生成的一键启动 bat 文件因换行符（LF/CRLF）和编码（UTF-8/GBK）问题在 Windows 上无法运行，排查后转换格式修复；
2. AI 写的测试断言假设"1 号设备有 100 多条记录"，实际 test 集设备只跑到中途（31 条），报错后核实数据修正断言；
3. AI 初版异常标注用全机群基线导致标不出异常，分析数据分布后改为设备自身基线。

### 6.4 人工审查

所有 AI 生成代码均经过逐行阅读与实际运行验证，关键逻辑（特征提取、规则匹配、阈值判定）由本人复核并能独立讲解。

## 7. 总结与展望

### 7.1 完成的工作

完成了一个架构完整（前端/后端/数据库/算法四要素齐全）、业务闭环可演示的设备健康管理系统，覆盖课程四个技术方向，全部通过自动化测试。

### 7.2 不足与改进方向

- LSTM 目前只用于对比实验，未接入系统在线推理；
- 数据集为单工况单故障（FD001），真实工业场景更复杂，可扩展到 FD002~FD004 多工况数据；
- 规则库靠人工编写，后续可研究从维修记录中自动挖掘规则。
